    Service Interface XML reference¶

    Baseline: Tala 31.0.2. The service interface declares operations referenced by domain plan items and binds them to parameters and transport targets.

    Operations and required structure¶

    The root <service_interface> contains action, query, and validator declarations. An action has this structure:

    <service_interface>
  <action name="BookRoom">
    <parameters>
      <parameter predicate="room_date" format="value"/>
      <parameter predicate="selected_room" optional="true"/>
    </parameters>
    <failure_reasons>
      <failure_reason name="unavailable"/>
    </failure_reasons>
    <target>
      <http endpoint="https://service.example/book-room"/>
    </target>
  </action>
  <query name="available_room">
    <parameters>
      <parameter predicate="room_date"/>
    </parameters>
    <target>
      <http endpoint="https://service.example/find-rooms"/>
    </target>
  </query>
</service_interface>

    The example endpoint is illustrative only; deployed endpoint values belong in service configuration.

    Operation Required children Accepted target forms
    action parameters, failure_reasons, target <frontend/> or <http endpoint="..."/>
    query parameters, target <http endpoint="..."/>
    validator parameters, target <http endpoint="..."/>

    Operation names must be unique within their type. A target is required. Query and validator frontend targets are rejected by Tala's XML compiler tests.

    For an action, keep the <parameters>, <failure_reasons>, and <target> children even when a section is empty. An empty failure list is written as <failure_reasons/>. Queries and validators do not have a failure_reasons child in the XML format.

    Parameters and results¶

    Each <parameter> requires an ontology predicate. Its optional format is value or grammar_entry; optional is an XML Boolean. For HTTP targets the service receives both the semantic value and the language grammar entry. The format selector chooses the frontend representation for frontend-targeted actions.

    HTTP actions may declare failure_reason names. Frontend-targeted actions must have an empty <failure_reasons/> section; the compiler rejects named frontend failure reasons while loading the Service Interface. For HTTP actions, the runtime does not enforce that an empty declaration means the operation always succeeds. The action result and any declared failure information are consumed by TDM's service-action execution and reporting logic.

    Parameter attribute Values Meaning
    predicate Required ontology predicate Selects the argument to bind and pass to the target.
    optional XML Boolean Marks the argument optional.
    format value or grammar_entry Selects the frontend argument form. HTTP targets receive both representations.

    For queries, name must match the ontology predicate of the question passed to the service. The runtime looks up and sends that predicate name; a domain service_query mapping selects a question rather than creating an operation alias.

    frontend delegates actions to the application-facing side. http invokes the declared HTTP endpoint; query and validator operations use this target.

    Compatibility boundaries¶

    The XSD declares an entity_recognizer element, but the ServiceInterfaceCompiler builds only actions, queries, and validators. Do not assume an entity-recognizer declaration is part of the runtime ServiceInterface model.

    The DDD JSON schema uses a shared target shape that permits a frontend target for all operation types. The XML compiler rejects frontend targets for queries and validators after JSON is converted to XML. Use HTTP targets for those operations and compile/load the bundle to validate it.

    Executable references: tala/ddd/schemas/service_interface.xsd, tala/ddd/schemas/json/service_interface.schema.json, tala/ddd/ddd_xml_compiler.py, and tala/ddd/test/test_ddd_xml_compiler.py.

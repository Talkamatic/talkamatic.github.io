    Plan items¶

    This page documents the remaining Tala 31.0.1 plan items. They are directives inside the ordered <plan>/<postplan> sequences or conditional branches described in Domain declarations. The XML language and plan-item set are defined by domain.xsd and the Tala compiler.

    Detailed pages for Findout, Bind, Conditions, Downdate conditions, and Invoke service action are separate.

    Questions and assumed facts¶

    raise¶

    <raise type="wh_question" predicate="destination"/>

    raise raises a question/issue for the user but does not put the same answer-resolution requirement on the current plan as findout. type defaults to wh_question; the question may be goal, WH, KPQ, alternative, or yes/no. It accepts the same question-content children as findout. The allow_answer_from_pcom and alts_predicate options belong to findout, not raise.

    assume_issue¶

    <assume_issue type="wh_question" predicate="departure_time"/>

    This opens a question issue as if the user had asked it. The issue should have a matching resolve goal in the DDD. It supports question content such as a KPQ's embedded_question; insist is an optional Boolean. Tala 31.0.1's XML compiler requires type, even though the schema leaves it optional.

    assume_shared and assume_system_belief¶

    Each contains a predicate proposition. assume_shared adds the fact to shared commitments; assume_system_belief adds it to private beliefs.

    <assume_shared>
  <proposition predicate="current_recipe" value="sourdough_starter"/>
</assume_shared>
<assume_system_belief>
  <proposition predicate="quantity" value="200"/>
</assume_system_belief>

    The proposition must use an ontology predicate and a value compatible with its sort. These are assertions of known state, not service calls or validators.

    inform¶

    <inform insist="false" generate_end_turn="true" expected_passivity="2.0">
  <proposition predicate="first_name" value="Charlie"/>
</inform>

    inform contains one predicate proposition. It makes the proposition shared and requests a system utterance. With the default insist="false", an existing shared value for that predicate suppresses the inform. With insist="true", the previous value for the predicate is forgotten before the new proposition is assumed and informed. generate_end_turn defaults to false; when true, the compiler also adds an end-turn with the specified expected_passivity (default 0.0 seconds).

    Forgetting state and requesting user actions¶

    forget and forget_shared¶

    Use a predicate attribute to forget every matching proposition or a proposition child to forget one value:

    <forget predicate="colour"/>
<forget>
  <proposition predicate="transport" value="train"/>
</forget>
<forget_shared predicate="colour"/>

    forget removes the target from private beliefs and shared commitments. forget_shared removes it from shared commitments while leaving private beliefs unchanged.

    forget_all¶

    <forget_all/>

    This is a broad dialog-state reset: active plan and goals, private beliefs, shared commitments, and previous utterance traces are cleared, then the top goal is restarted. It has no attributes or children; use it only when restarting the dialogue is intended.

    get_done¶

    <get_done action="add_water" step="1"/>

    action is a required ontology action; step is an optional integer. The system asks the user to carry out that action. The item completes when the user reports that the action is done. A get_done may contain alt children to represent alternative actions.

    Branching and sequencing¶

    if¶

    <if>
  <has_shared_value predicate="sourdough_status"/>
  <then><jumpto type="perform" action="freshen_up_sourdough"/></then>
  <else><jumpto type="perform" action="start_sourdough"/></else>
</if>

    if contains exactly one condition expression, followed by optional then and else plans. Either branch may itself contain plan items, including nested if items. A missing branch does nothing.

    once¶

    <once id="initial_greeting">
  <inform>
    <proposition predicate="welcome_message" value="welcome"/>
  </inform>
</once>

    once wraps a plan sequence and runs it once for its marker. With no id, Tala assigns a unique marker. Reusing an id shares the once-state across blocks. The marker is kept in private beliefs, so forgetting it makes the block eligible to run again.

    jumpto¶

    <jumpto type="perform" action="freshen_up_sourdough"/>

    jumpto accepts a goal descriptor. Tala's compiler requires type; for a perform-goal target, supply its ontology action. The target plan is loaded, then the original plan resumes from its beginning. An unguarded jump may be encountered repeatedly; guard it with if or once. A jump in a completed resolve goal's postplan does not have that loop behavior.

    change_ddd¶

    <change_ddd name="navigation"/>

    name selects another DDD for the session. A domain change replaces the current DDD-specific plan/goal context; it is not a jump to a goal within the same domain.

    Queries and iterators¶

    invoke_service_query¶

    <invoke_service_query type="wh_question" predicate="price"
                      min_results="1" max_results="2"/>

    Invokes the service-interface query associated with the question. type defaults to wh_question; min_results and max_results default to 1. Raise max_results when multiple service results are expected. Question content may use the applicable proposition or embedded-question children.

    invoke_domain_query¶

    <invoke_domain_query type="wh_question" predicate="price"/>

    Invokes the top-level domain query matching the question in the active DDD. The Tala compiler sets both result bounds to one for this plan item.

    iterate¶

    <iterate iterator="nice_destinations"/>

    iterator is required and names a top-level iterator. The item assumes the next proposition in its enumeration. Use <has_more_items iterator="nice_destinations"/> to test whether values remain.

    reset_domain_query¶

    <reset_domain_query type="wh_question" predicate="season_to_consider"/>

    Resets enumeration state for the domain query identified by the question. The question uses the same type/child syntax as findout and domain queries.

    Status, turn-taking, and diagnostics¶

    signal_action_completion¶

    <signal_action_completion postconfirm="false"/>

    Signals that the containing perform goal is complete, stopping the remainder of its plan. By default, TDM reports a successful action-status move; postconfirm="false" suppresses that report. An optional action targets a named ontology action instead of the containing goal.

    signal_action_failure¶

    <signal_action_failure reason="service_unavailable"/>

    reason is required. Without action, it aborts the containing perform goal and stops the rest of its plan. With action, it marks that action aborted and allows the containing plan to continue. The failure reason is a result label; it is not declared in the ontology.

    end_turn¶

    <end_turn expected_passivity="1.5"/>

    expected_passivity is a required decimal number of seconds. end_turn hands the turn to the client/user at that point even if the DME otherwise has more plan content. It controls this explicit handoff, not passivity timing globally.

    log¶

    <log message="About to invoke BookRoom" level="debug"/>

    message is required. level is optional and defaults to debug in Tala's compiler. The log entry is diagnostic, not a user-facing dialogue move.

    greet¶

    <greet/>

    An empty plan item that requests a greeting move.

    DDD JSON¶

    Plan items use a single-key object in DDD JSON. For example:

    {"forget": {"predicate": "colour"}}
{"if": {"condition": {"has_value": {"predicate": "destination"}}, "then": [{"greet": {}}]}}
{"once": {"id": "initial_greeting", "content": [{"greet": {}}]}}
{"signal_action_failure": {"reason": "service_unavailable"}}

    The exact payload schemas are under tala/ddd/schemas/json/domain.schema.json.

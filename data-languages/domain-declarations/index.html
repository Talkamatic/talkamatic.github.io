    Domain declarations¶

    This page covers Tala 31.0.1 declarations outside the individual plan-item pages: goals/plans, question parameters, queries, iterators, validators, Other plan items.

    Goal¶

    A goal declares either an action the system can perform or a question it can resolve. Tala's XML compiler requires type even though the XSD does not mark it required. A perform goal needs an ontology action; a resolve goal describes a question.

    <goal type="perform" action="book_room">
  <plan>
    <findout type="wh_question" predicate="room_date"/>
    <invoke_service_action name="BookRoom"/>
  </plan>
</goal>
    Attribute Type Behavior
    type perform or resolve Required by Tala's XML compiler.
    action string Ontology action for a perform goal.
    question_type question type Resolve-goal question type; defaults to wh_question.
    predicate string Predicate for predicate-based questions.
    accommodate_without_feedback Boolean Suppresses the usual accommodation feedback.
    reraise_on_resume Boolean Controls whether feedback is produced when a goal resumes.
    restart_on_completion Boolean Restarts the goal when it completes.
    max_answers integer Maximum number of answers returned for a user question.
    alternatives_predicate string Predicate used to distinguish answers when several alternatives are allowed.

    A goal can have one plan, a postplan, zero or more downdate_condition elements, and preferred, proposition, superaction, and legacy postcond children. Current completion behavior should use explicit downdate conditions. Postplans are for bookkeeping after a resolve goal is resolved or downdated; author them on resolve goals.

    For a resolve goal with question_type="yn_question", include a proposition child to define the yes/no question. <preferred/> marks a goal as preferred unconditionally; a preferred proposition makes it preferred when that fact is present. Each superaction names an ontology action that groups the goal's action under a broader action. The schema retains postcond as a compatibility element, but the current compiler does not process it; use downdate_condition instead.

    <goal type="perform" action="book_room">
  <preferred>
    <proposition predicate="travel_mode" value="business_class"/>
  </preferred>
  <superaction name="arrange_travel"/>
  <plan><invoke_service_action name="BookRoom"/></plan>
</goal>
<goal type="resolve" question_type="yn_question">
  <proposition predicate="need_visa" value="true"/>
</goal>

    Plan and postplan¶

    plan is an ordered sequence of plan items. The order defines the preferred dialogue path, while the DME may respond to user input using general dialogue capabilities. See the plan-item reference.

    postplan is also ordered. It runs after a resolve goal completes and is intended for bookkeeping, such as forgetting temporary information or moving to a follow-up goal. A jump from a completed goal's postplan does not repeat the completed source plan.

    Question parameters¶

    A parameters declaration keys on a predicate, optionally qualified by question_type. Its attributes in domain.xsd include:

    Attribute Values / meaning
    question_type Question type; omitted for the default wh-question form.
    predicate Question predicate.
    source domain or service; incremental-search result source.
    incremental Enables incremental search.
    verbalize Controls whether the question is verbalized.
    allow_goal_accommodation Allows goal accommodation for the question.
    always_ground Controls grounding behavior.
    max_spoken_alts Maximum alternatives spoken; minimum 1.
    max_reported_hit_count Maximum hits reported; minimum 1.
    on_zero_hits_action Action run for zero hits.
    on_too_many_hits_action Action run when there are too many hits.
    sort_order Currently alphabetic.

    The XML schema permits these children:

    • service_query — question used as the service query.
    • ask_feature — feature predicate to ask about; kpq="true" asks whether the user knows the embedded feature value.
    • alt — explicit proposition alternatives.
    • hint — contains one inform item, presented after negative acceptance.
    • proposition, resolve, perform — typed question/goal content.
    • related_information — related questions.
    • always_relevant — marks the question relevant across topic changes.

    For incremental search with source="service", define service_query; the ask-features refine the search. background and graphical_type are not in the Tala 31.0.1 XML schema and should not be copied from historical examples.

    Domain query¶

    A top-level <query> requires a predicate and one of three mutually exclusive query bodies:

    1. One or more <implication> elements. The antecedent may contain a single predicate proposition or a configuration of propositions; all propositions in a configuration must hold. Make the cases exhaustive for the expected state space.
    2. <select_at_random>, containing one or more individuals. A later call may return the same item again.
    3. <enumerate>, containing one or more individuals. Values are returned in declaration order; randomize="true" changes that order randomly.
    <query predicate="greeting">
  <implication>
    <antecedent predicate="time_of_day" value="morning"/>
    <consequent predicate="greeting" value="good_morning"/>
  </implication>
  <implication>
    <antecedent predicate="time_of_day" value="evening"/>
    <consequent predicate="greeting" value="good_evening"/>
  </implication>
</query>

    invoke_domain_query resolves a question through the matching domain query. An enumeration restarts after its final value; use has_more_items when the dialogue must distinguish the last item.

    Iterator¶

    An <iterator> requires a name and one <enumerate> child. Its <enumerate> contains propositions and may specify randomize and limit.

    <iterator name="room_iterator">
  <enumerate randomize="false" limit="5">
    <proposition predicate="room_type" value="single"/>
    <proposition predicate="room_type" value="double"/>
  </enumerate>
</iterator>

    iterate assumes the next proposition. The has_more_items condition can branch once the iterator is exhausted.

    Domain validator¶

    A domain-level validator describes accepted configurations of propositions. Its name identifies the validator; each configuration is a conjunction of propositions. This is different from a Service Interface validator, which is an external service operation.

    <validator name="DestinationValidity">
  <configuration>
    <proposition predicate="destination" value="karlstad"/>
  </configuration>
  <configuration>
    <proposition predicate="destination" value="gothenburg"/>
  </configuration>
</validator>

    The Tala XML compiler reads configuration children, and DDD JSON represents the same information in valid_configurations. The domain XSD's named validator type is less specific than the compiler's effective structure.

    Defaults and dependencies¶

    Each top-level <default_question> declares a question that is considered by default in the domain. A <dependency> identifies a dependent question with its own type/predicate and one or more <question> children that it depends on. The relation marks those questions as connected for relevance handling.

    <dependency type="wh_question" predicate="room_date">
  <question type="wh_question" predicate="room_type"/>
</dependency>

    Source formats¶

    Tala 31.0.1 defines the XML structure in tala/ddd/schemas/domain.xsd and compiles it in tala/ddd/ddd_xml_compiler.py. The corresponding DDD JSON properties are defined in tala/ddd/schemas/json/domain.schema.json; see DDD JSON for the source bundle form.
